# Database Tables

The database stores users and the metadata of their saved documents. The file contents themselves live in the object store (S3 or local disk) and are found through each document's `object_key`. The schema is defined in `src/storage/database.py` with SQLAlchemy Core, so the same three tables are created on SQLite locally and PostgreSQL on RDS.

```
users 1 ──── * documents 1 ──── * document_tickers
```

# users

**Purpose:** One row per registered account. It holds the login credentials and is the owner that each document points to.

| Column | Type | Description | Example |
|---|---|---|---|
| `user_id` | Integer, primary key | Auto-incrementing id of the user. | `1` |
| `username` | String(32), unique, required | Login name. Must be unique, so creating a duplicate raises an `IntegrityError`. | `finn` |
| `password_hash` | String(255), required | Hash of the password. The plain password is never stored. | `$2b$12$KIX...` |
| `is_admin` | Boolean, required, defaults to false | Whether the user is an admin. An admin can see and delete every document, private or public. Sign-up always creates `false`; only the seed script (`src/storage/seed.py`) creates an admin. | `false` |
| `created_at` | DateTime (timezone-aware), required | When the account was created, in UTC. | `2026-10-26 06:05:00+00:00` |

**Seeded accounts:** when the dashboard starts, `seed_accounts` creates any of `admin` (admin), `alice`, `bob` and `carol` that do not exist yet. Each gets a random password. With `--local` it is appended to `local-data/seed-credentials.txt` (gitignored). On AWS it is saved as the SecureString `/work/stock-research/seed/<username>` in SSM Parameter Store. Running it again creates nothing. If two web servers create the same account at once, the unique `username` makes the second insert fail, and that server skips the account. On a database created before `is_admin` existed, `Database` adds the column on startup.

# documents

**Purpose:** One row per saved document, whether generated by the dashboard (overview, single-stock or statements report) or uploaded by the user. It stores the document's description, ownership and access level. The file itself is stored in the object store under `object_key`.

| Column | Type | Description | Example |
|---|---|---|---|
| `document_id` | Integer, primary key | Auto-incrementing id of the document. | `7` |
| `owner_id` | Integer, foreign key to `users.user_id`, required | The user who owns the document. Deleting the user deletes their documents (`ON DELETE CASCADE`). | `1` |
| `filename` | String(255), required | Name of the file when downloaded. Built from the tickers (or the title for uploads), the document type and a UTC timestamp. | `AAPL-vs-MSFT_overview_20261026-060500Z.md` |
| `object_key` | String(512), unique | Location of the file in the object store. Empty until it is set in the same transaction that creates the row, because it contains the `document_id`. | `users/1/7/AAPL-vs-MSFT_overview_20261026-060500Z.md` |
| `title` | String(255), required | Display name shown in the document list. | `AAPL vs MSFT` |
| `document_type` | String(16), required | Kind of document. Must be one of `overview`, `single`, `statements` or `upload` (checked by `ck_documents_type`). | `overview` |
| `visibility` | String(8), required | Who can see the document. `private` is visible only to the owner, and `public` is visible to everyone. Must be one of those two values (checked by `ck_documents_visibility`). | `private` |
| `content_type` | String(64), required | Media type of the file, used when downloading or previewing it. | `text/markdown` |
| `size_bytes` | Integer, required | Size of the file in bytes. | `18432` |
| `sha256` | String(64), required | SHA-256 hash of the file contents, as hex. Used to check integrity. | `9f86d081884c7d659a2f...` |
| `start_date` | Date, optional | Start of the price range analysed. Empty for documents with no range, such as uploads. | `2021-10-26` |
| `end_date` | Date, optional | End of the price range analysed. | `2026-10-26` |
| `range_label` | String(32), optional | The time range option chosen in the sidebar: `1 year`, `5 years`, `10 years`, `20 years` or `Custom`. | `5 years` |
| `created_at` | DateTime (timezone-aware), required | When the document was saved, in UTC. Newest documents are listed first. | `2026-10-26 06:05:00+00:00` |

**Check constraints**

A check constraint makes the database reject any row whose value is outside the allowed list, so an invalid value cannot be saved even if the application code has a bug. The allowed values come from `VISIBILITIES` and `DOCUMENT_TYPES` in `src/storage/database.py`, which `DocumentStore.save` also validates against before inserting.

| Constraint | Column | Rule | Allowed values |
|---|---|---|---|
| `ck_documents_visibility` | `visibility` | `visibility IN ('private', 'public')` | `private`, `public` |
| `ck_documents_type` | `document_type` | `document_type IN ('overview', 'single', 'statements', 'upload')` | `overview`, `single`, `statements`, `upload` |

An insert or update that breaks a rule fails with an `IntegrityError`. To allow a new value, add it to the list in `database.py`. Because `create_all` skips tables that already exist, an existing database also needs its constraint changed with a migration or `ALTER TABLE`.

**Indexes**

| Index | Columns | Used for |
|---|---|---|
| `ix_documents_owner_created` | `owner_id`, `created_at` | The `owner_id = :user_id` half of the visibility filter (`owner_id = :user_id OR visibility = 'public'`), which finds a user's own documents. Because `created_at` is second, rows come out already in newest-first order, so no separate sort is needed. |
| `ix_documents_visibility_created` | `visibility`, `created_at` | The `visibility = 'public'` half of the same filter, which finds every public document, newest first. Visitors who are not logged in see no documents, so they run neither half. Without it, the `OR` would force a scan of the whole table, reading every private document just to skip it. It helps most when public documents are a minority, since `visibility` has only two values. At this project's scale it is cheap insurance rather than a measurable speed-up. |

# document_tickers

**Purpose:** Links each document to the stock tickers it covers. One document can cover many tickers (for example a comparison of three stocks), so the tickers are kept in their own table instead of a column on `documents`. Each (document, ticker) pair is one row.

| Column | Type | Description | Example |
|---|---|---|---|
| `document_id` | Integer, foreign key to `documents.document_id`, part of primary key | The document the ticker belongs to. Deleting the document deletes its ticker rows (`ON DELETE CASCADE`). | `7` |
| `ticker` | String(16), part of primary key | Stock symbol. Together with `document_id` it stops the same ticker being listed twice for one document. | `AAPL` |
| `position` | Integer, required | Zero-based order in which the ticker was entered, so the original order can be rebuilt. | `0` |

**Primary key:** the composite `(document_id, ticker)`, declared by setting `primary_key=True` on both columns.

- The pair must be unique, not each column on its own. Document `7` can have many tickers, and `AAPL` can appear in many documents. Only a second `(7, AAPL)` row is rejected, which stops the same ticker being listed twice for one document.
- No separate id column is needed, because the pair already identifies a row.
- The database builds an index for the key, sorted by `document_id` first. That makes "tickers for document 7" fast, and it is why the separate `ix_document_tickers_ticker` index below is needed for lookups by ticker alone.
- `position` is not part of the key. It only stores the order and can repeat across documents.

**Indexes**

| Index | Columns | Used for |
|---|---|---|
| `ix_document_tickers_ticker` | `ticker` | Finding every document that covers a given ticker, as the **Tickers** search filter does (one lookup per selected ticker, all of which must match). The primary key is sorted by `document_id` first, so it cannot serve this lookup. |

**Example rows** for document `7`, a comparison of `AAPL` and `MSFT`:

| document_id | ticker | position |
|---|---|---|
| 7 | AAPL | 0 |
| 7 | MSFT | 1 |
